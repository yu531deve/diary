# 作問パイプライン（Sonnet 下書き → オーケストレーター規約レビュー → Yu 検収）

- 版: v1.0（issue #102）
- 目的: 院試向け 1000 問規模を目指すにあたり、作問→検収→公開の流れを定型化する。
  現状は `content/0001/`（issue #99 / PR #269 で差し替え）が唯一の実例であり、これを型として量産運用に一般化する

## 1. フロー概要

```
1. Sonnet（worktree）
   - /new-problem で雛形生成 → problem.tex / solution.tex / meta.yaml を執筆
   - status: draft のまま PR 作成（published は絶対に付けない。不変条件 4）
   - PR 本文に難易度査定の根拠・別解の有無・懸念点を明記

2. オーケストレーター（Fable ほか）による規約レビュー
   - 本文 §3 のチェックリストで機械的に確認できる項目を先に潰す
   - content/CLAUDE.md・docs/difficulty.md・tags.yaml/fields.yaml との整合を確認
   - 数学的な正しさそのものの最終判定はしない（次段の Yu 検収に委ねる）が、
     明らかな計算間違い・論理の飛躍に気づいた場合は指摘してよい

3. Yu の最終検収
   - 数学的正しさ・難易度査定・記法規約を確認
   - 問題なければ meta.yaml の status を draft → published に変更してマージ
   - published への引き上げは Yu のみが行う（不変条件 4、content/CLAUDE.md 「禁止」節）
```

この 3 段構成は PR #269（issue #99: 問題 0001 の差し替え）を型とする。同 PR は

- Sonnet が下書きし、PR 本文冒頭に「Yu の検収が必要です」と明記した
- 元々 `status: published` だった 0001 を、内容を丸ごと差し替えるため `draft` に戻した
- 難易度査定の根拠（知識の範囲・発想の要求度）を `docs/difficulty.md` の基準文に対応づけて PR 本文に書いた
- Definition of Done の 4 項目それぞれの充足状況を明記した
- `make check`（devcontainer 上の検証）までは未実施である旨を隠さず記載した

という点で、以降の作問 PR が踏襲すべき型になっている。

## 2. 各段階の責務

### 2.1 Sonnet（下書き段階）

- `/new-problem` スキルで雛形を生成する（`content/{id}/` に `meta.yaml` / `problem.tex` / `solution.tex`）
- `content/CLAUDE.md` の LaTeX 執筆ルール・記法規約に従う
- `fields.yaml` / `tags.yaml` に存在する値のみを `meta.yaml` に書く。存在しない値が必要な場合は
  辞書に無断で追加せず、issue を立てて提案する（保護ファイルのため）
- 難易度は `docs/difficulty.md` の 5 段階表を根拠に自己査定し、判断理由を PR 本文または
  `meta.yaml` のコメントに書く
- `status: draft` のまま PR を作成する。`published` には絶対にしない
- `make lint` を通す。PDF・HTML 生成の確認は一時的に `published` に切り替えて手元検証してよいが、
  コミットする最終状態は `draft` に戻す（PR #269 の手順を踏襲）
- 1 PR = 1 問題（`content/CLAUDE.md` の禁止事項に従い、他の問題ディレクトリには触れない）

### 2.2 オーケストレーター（規約レビュー段階）

- §3 のチェックリストのうち、記法規約・タグ辞書準拠・meta.yaml スキーマなど機械的に照合できる項目を確認する
- `make lint` が通っているか、Definition of Done の該当項目が満たされているかを PR の記載から確認する
- 数学的正しさ・別解の妥当性・難易度査定の最終判断は行わない（Yu 検収に委ねる）。ただし明白な誤りに
  気づいた場合はレビューコメントで指摘し、Sonnet に差し戻してよい
- 規約上の問題がなければ Yu にレビュー依頼として引き継ぐ

### 2.3 Yu（最終検収段階）

- §3 のチェックリスト全体、特に数学的正しさ・難易度査定を確認する
- 問題なければ `meta.yaml` の `status` を `draft` から `published` に変更し、PR をマージする
  （マージ自体は検証が通っていればオーケストレーターが代行してよいが、`published` への変更は Yu が行う）
- 修正が必要な場合は PR にコメントし、Sonnet の worktree に差し戻す

## 3. 検収チェックリスト

作問 PR のレビュー・検収では、以下を確認する。オーケストレーターは主に A・B、Yu は全項目を確認する。

### A. 記法・規約準拠（オーケストレーターが主に確認）

- [ ] `meta.yaml` のスキーマが `content/CLAUDE.md` と一致している（`id` がディレクトリ名と一致、
      `status: draft`、`created`/`updated` が妥当な日付）
- [ ] `field.major` / `field.minor` が `fields.yaml` に存在する値である
- [ ] `tags` が `tags.yaml` に存在する値のみで構成されている
- [ ] LaTeX 本文にドキュメントクラス・プリアンブル・`\usepackage` を書いていない
- [ ] ベクトル・行列・作用素・積分・集合の記法が `content/CLAUDE.md` の「大学以降の記法の書き方」に従い、
      1 問題内で表記が統一されている
- [ ] `make lint` が通っている（禁止コマンド・メタデータ・タグ辞書チェック）
- [ ] 他の問題ディレクトリに変更が及んでいない（1 PR = 1 問題）
- [ ] `status: published` になっていない

### B. ビルド（Definition of Done との対応）

- [ ] PDF（問題・解答）が生成される
- [ ] HTML 変換が通る、またはフォールバックが正しく動作する（失敗した場合は PR 本文に明記されている）
- [ ] TikZ 図がある場合、SVG 化される

### C. 数学的内容（Yu が最終判断）

- [ ] 解答が厳密に正しい（論理の飛躍・場合分けの漏れがない）
- [ ] 別解が想定できる場合、解答例に含まれている、または検討した旨が PR 本文にある
- [ ] 検算（数値例・特殊ケースでの整合性チェックなど）が行われている、または検算可能な形で解答が書かれている
- [ ] 難易度査定が `docs/difficulty.md` の基準表と整合しており、判断根拠が明記されている
- [ ] 問題文に曖昧さ・多義的な解釈の余地がない

## 4. `/new-problem` スキルとの整合確認（issue #102 時点）

`.claude/commands/new-problem.md` の内容を確認した結果、以下の点で現行の分野辞書・執筆規約と
既に整合しており、追随のための変更は不要と判断した。

- 雛形生成の手順は「既存最大 ID + 1」「`content/CLAUDE.md` のスキーマに従う」「`make lint` で確認」
  という一般的な記述であり、分野名・タグを固定でハードコードしていない
- したがって `fields.yaml`（8 分野、issue #92 で刷新済み）や `tags.yaml`（issue #101 で刷新済み）が
  改定されても、スキル自体の修正は不要な構成になっている

一方で、ドキュメント間の表記に軽微な揺れを見つけた。`content/CLAUDE.md` の出題範囲の説明文で
分野名を「偏微分方程式と積分変換」と書いているが、`fields.yaml` 上の正式名称は
「偏微分方程式・積分変換」であり、区切り文字が異なる。`content/CLAUDE.md` は保護ファイルではないため
本 PR で追随可能だが、`content/CLAUDE.md` 自体の記述修正は本 issue のスコープ（作問フロー文書化）外
であり、別 issue を立てて相談する（`fields.yaml` は保護ファイルのため、修正の要否含め単独判断しない）。

## 5. バッチサイズ・並列本数（Yu 確定待ち）

1 バッチあたりの問題数・並列 worktree 数は本 issue の受け入れ条件上「決めずに提案する」ことに
なっているため、以下は根拠付きの提案であり、**未確定（Yu 確定待ち）**。

### 論点

- 効率（スループット）を優先すれば並列本数・バッチサイズは大きい方がよい
- レビュー品質（オーケストレーター規約レビュー・Yu 検収の負荷）を優先すれば小さい方がよい
- `content/CLAUDE.md` の禁止事項により 1 PR = 1 問題が原則なので、「バッチ」は
  「同時に worktree で走らせる PR 数」と実質的に同義になる

### 提案（叩き台）

- **1 バッチ = 3〜5 問題（PR 3〜5 本）を目安とする**
  - 根拠: PR #269 のような単一 PR の検収（難易度査定の妥当性・別解確認・記法確認）には
    Yu 側で相応の時間がかかる。5 本を超えると 1 セッションでの検収が滞留し、
    `draft` のまま積み上がって差し戻しのフィードバックループが遅くなるリスクが上がる
- **並列 worktree 本数も 3〜5 本を上限の目安とする**
  - 根拠: `content/CLAUDE.md` により 1 PR = 1 問題 = 独立した `content/{id}/` ディレクトリなので
    worktree 間の衝突リスクは低い（保護ファイルにさえ触れなければ ID 採番以外の競合が起きにくい）。
    ただし ID 採番（既存最大値 + 1）は並列度が上がるほど衝突しやすくなるため、
    採番タイミングをずらす・PR 作成直前に再確認するなどの運用が必要になる
- 分野・難易度の偏りを避けるため、1 バッチ内では分野（`fields.yaml` の 8 分野）を
  分散させることが望ましい（例: 1 バッチ 5 問なら異なる大分野から選ぶ）

### 確定が必要な理由

- 数値そのもの（3〜5 という範囲・上限）を最終的に決めるのは、Yu の検収に割ける時間・
  レビュー体制の見通しに依存し、本 issue の担当者（Sonnet）が把握できる情報ではないため
